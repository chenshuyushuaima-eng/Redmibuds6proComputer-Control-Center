# 0.1.7 连接修正、贴合度流程与佩戴配置区分

适配 REDMI Buds 6 Pro 国行（VID/PID `2717/509D`，固件 `1.1.9.9`）。依据为用户提供的小米耳机 `com.mi.earphone` 1.38.0 APK，以及本地蓝牙日志。此次未发送实机检测指令或播放检测音频。

## 佩戴检测

0.1.4 错将配置 `06` 同时用于佩戴开关解析，但该配置实际为贴合度结果。官方 `DeviceSetMoreFragment$initListener$3` 使用 `getConfigByType(0x7E)` 读取 `DeviceConfigWearDetection`。其 `valueToParams` 明确区分 `[subCmd,subValue]`：子命令 `00` 是佩戴检测，`01` 是语音控制，开关在第二字节。

官方 `FunctionConfigImpl.wearChecked` 使用运行设置命令 `08`，参数 `[02,06,value]`，`value=0` 开启，`value=1` 关闭。`DeviceSetMoreFragment$initListener$2` 也从运行状态 `autoPlay` 读取开关；`$initListener$3` 只在配置子命令为 `00` 时读取 `subValue`。

写入参数的供应商类型 `06` 与运行信息的返回字段不同：`09` 响应中的 `0A` 为 `autoPlay`。2026-10-04 12:18:05 日志中，写入 `[02,06,01]` 后返回 `02-0A-01`；12:19:34 写入 `[02,06,00]` 后返回 `02-0A-00`。两个时刻运行条目 `06` 都保持为零，故不能用它验证佩戴开关。0.1.6 沿用 0.1.4 的 `0A` 回读字段。

新版将运行状态与配置子命令分开保存，显示时优先使用实时运行状态；设置后重新请求 `09`，直接检查本次应答的 `0A` 字段。配置读取不会覆盖刚取得的实时值，佩戴检测的配置推送可更新开关；语音控制子命令不会影响佩戴检测。

该开关控制耳机端自动播放/暂停行为；Windows 播放器仍需支持耳机发送的播放控制。

## 0.1.6 连接回归与 0.1.7 修正

2026-10-04 15:54–15:56 日志显示：RFCOMM 连接与双向认证成功，设备信息 `02`、运行状态 `09` 及原有配置查询均有正常回复；新增的 `F3 [00,7E]` 始终没有回复，随后查询超时或控制连接断开，初始化失败。另一次断线后仍继续发送空间音频查询，说明非必需配置的异常处理也未及时停止。

APK 中的 `getConfigByType(0x7E)` 是配置对象的访问方式，不能据此确认此固件支持直接 `F3 [00,7E]` 查询。0.1.7 从主动查询列表移除 `7E`，恢复 0.1.4 的列表；保留 `7E` 推送解析，并通过已验证的 `09/0A` 读取佩戴开关。非必需配置超时记录后跳过，实际断线则停止查询并报告失败；认证、设备信息和运行状态的必需请求仍须成功。

## 贴合度检查协议和流程

官方 `DeviceConfigFit`、`FunctionConfigImpl.setSwitch` 与 `FitDetectionViewModel` 定义：

- 启动：`F2`、配置 `05`、值 `[01]`；停止值 `[00]`。
- `FitDetectionFragment$onViewCreated$1` 使用 `getConfigByType(0x06)` 接收 `DeviceConfigFit`。因此 `F4` 配置 **`06`** 推送 `[left,right]`，与启停配置 **`05`** 不同。
- 一侧返回 `3` 表示进入检测状态，官方在这个状态启动音频播放。
- 结果 `1` 表示贴合良好，`2` 表示需要调整；官方仅在双耳均为 `1/2` 时将本次测量判为完成。
- `9` 表示双耳未保持佩戴，`10` 表示通话阻止检查。其余值不伪造为成功结果。
- 官方超时为 10 秒。

既有实机日志（2026-10-04 12:17）记录了以下通知，配置码位于负载 `04-00-06-...` 中：

```text
就绪：FE-DC-BA-87-F4-00-06-03-04-00-06-03-03-EF
良好：FE-DC-BA-87-F4-00-06-07-04-00-06-01-01-EF
调整：FE-DC-BA-87-F4-00-06-0D-04-00-06-02-02-EF
```

0.1.4 监听 `05`，无法接收这些 `06` 结果，因而超时。0.1.6 在 `Protocol` 中分别定义启停码与结果码，接收分支使用结果码，同时将佩戴配置匹配移至 `7E`，消除配置冲突。就绪后启动音频的官方调用链为 `onDetectionChanged(3)` → `FitDetectionViewModel.startResponse()` → ExoPlayer `play()`。

实现先停止旧检测，再建立本次会话并启动。只接收本次会话中的配置推送，等待进入检测状态后播放音频，等待双耳结果。没有进入检测状态时不播放，也不采用缓存配置作为本次结果。协议本身没有检测会话编号，故通过停止旧检测、等待新就绪状态与超时限制减少旧推送的影响。

检测期间串行占用命令通道，界面禁用其他耳机设置、查找、重连与周期刷新。取消会立即停止本机音频，再发送停止检测命令；断线、超时、完成、缩小到托盘和完全退出同样结束播放。关闭选择框中点“取消”不会中断检查。停止命令失败会记录日志或显示错误。

## 检测音频和 Windows 输出

`resources.arsc` 映射：`0x7f130006 raw/fitness_detect` → `res/Pir.wav`。原文件为立体声、44100 Hz、24 位 PCM，时长约 10.55 秒。官方使用 ExoPlayer 重复播放。

Windows 使用 `waveOut` 明确选择名称包含 `Buds 6 Pro` 的立体声输出，排除标识为免提的输出，保留用户对输出设备的选择；没有符合条件的输出时禁用开始按钮。播放前检查输出编号与名称是否仍匹配，不自动回退到电脑默认扬声器。24 位样本转换为 16 位 PCM 以适配 Windows 播放，不改变采样率、声道或增益；程序不调整系统音量。

音频保存在独立文件中，需和可执行文件一起保留。公开源码和 Windows 包不含官方音频，由使用者从自己的 APK 提取，见 [音频准备说明](fit-audio.md)。资源的来源与许可范围见 `THIRD_PARTY_NOTICES.md`。
